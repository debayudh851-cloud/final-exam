TalentDesk assessment prototype — assumptions and limits

1. Scope: one integrated Django 5 project, PostgreSQL persistence, Django templates, JWT/DRF, Celery/Redis, and local ML/NLP/Keras. No external LLM APIs. All seed candidates are synthetic and addresses use example.test.
2. Duplicate key: normalized email, globally unique. This prototype allows one application per email; multi-role reapplications would require a separate Application model.
3. Roles: public signup always creates HR, and verification gates access. Admin creates/assigns interviewer/admin accounts. Console email is the local executable verification delivery mode; actual SMTP needs configuration. OTP is hashed, expires after ten minutes, and stops after five wrong attempts; create a fresh test registration or ask an admin to reset an exhausted verification state. There is no resend workflow in this prototype.
4. PostgreSQL settings come from .env. Database secrets, .env, installed packages, logs, and user uploads are excluded from the source ZIP. Only explicitly documented disposable demo application credentials appear in README.
5. Large imports: 100+ rows are Celery jobs; up to 50,000 rows/20 MB. Pandas parses the bounded input during preflight and again in the worker. Database screening/insertion happens in the worker; this is not an unbounded streaming importer. .xlsx is supported, .xls is not.
6. Accepted insertions and final batch completion are atomic. Progress is published separately every 25 rows. Replaying completed work is a no-op; importing the same file again rejects duplicates. A hard-killed worker needs operator recovery, documented in README. Redis runs with no persistence in the helper; a machine restart can lose queued broker messages and needs the same recovery. No automatic task retry silently changes records.
7. Windows: checksum-verified community Redis 8.2.10 build; Celery solo pool. Celery does not officially support Windows. The local worker path has been tested here; standard Redis/Celery on Linux/WSL is preferable for wider deployment. No Docker/OS services were installed.
8. ML training data: 240 generated records, random seed 42, selected/rejected labels from a documented synthetic rule plus 12% noise. Split: 180 train, 60 test, stratified. Candidate features: experience, notice period, salary, unique skill count, role. College/identifiers/name/email/phone/target/resume are excluded to avoid leakage and irrelevant identity signals. Missing numeric values are median-imputed; role categories are encoded; outlier caps and normalization are train-fitted.
9. Logistic Regression and Random Forest are compared on the same holdout. F1 then AUC choose the demonstration artifact. Because selection uses this holdout, reported scores are not an independent final estimate. Real evaluation needs representative consented labeled data, an independent evaluation set, bias analysis, and HR oversight. Scores do not automatically decide employment or overwrite original candidate fields.
10. NLTK uses resource-free wordpunct tokenization and a downloaded English averaged perceptron POS tagger. TF-IDF is fitted to each resume to demonstrate numerical text features, not cross-document retrieval or semantic similarity. Skill phrases are matched case-insensitively with word boundaries. Blank resume returns empty tags/vector and zero. POS inputs are limited to 500 tokens and vectors to 100 terms for the demo. Original resume text is retained.
11. Keras CPU ANN: 16/8 ReLU hidden units, one sigmoid output, historical selected/rejected target, 15 epochs of minibatch updates. It saves preprocessing/model, reloads, and invokes inference. Small synthetic dataset and weak features demonstrate execution, not useful hiring quality. It is a management-command prototype, not an ANN HTTP endpoint (the required secured prediction endpoint serves the chosen Scikit-learn model).
12. Optional resume/PDF/docx/text and image files are upload/download attachments. No resume OCR or document parsing is claimed. Media and export downloads require HR/Admin access. Inputs are bounded, templates escape text, AJAX POST checks CSRF, passwords/OTP are hashed, and raw error traces stay in logs.
13. JWT logout revokes refresh, not an already issued access token. Access expires after 15 minutes; refresh rotates and old refresh is blacklisted. Invalid/expired tokens return 401. Candidate management and ML/NLP require HR/Admin; assigned-slot/feedback policies restrict interviewers.
14. NATURAL JOIN base tables is unsafe because their shared id has different meaning. sql_queries.sql projects each side so applied_role_id is the only shared name and supplies an explicit equivalent. FULL OUTER JOIN cannot show orphan candidates because the real FK prevents them, but shows empty roles.
15. Core Python concepts are used in the real ingestion workflow. CandidateValidator deep-copies nested global validation policy to isolate instances. RowValidationError recursively flattens grouped field errors for rejected exports. rejected_record shallow-copies scalar raw fields before adding metadata. BatchCounts.__add__ combines accepted/rejected row outcomes. iter_records uses an iterator with while/break, and process_batch uses continue to skip invalid database inserts. A nonlocal closure numbers rows/progress. Phone normalization uses indexing/slicing for international prefixes. ingestion/python_concepts.py now demonstrates these same production helpers rather than separate examples.
16. This is a local assessment application. Advanced production features such as interview overlap locks across concurrent scheduling requests, malware scanning, recruitment fairness auditing, retention controls, and deployment hardening are outside this prototype. Admin form editing has Django validation but is not a substitute for the ingestion/API workflow for dirty bulk records.
17. The protected candidate JSON collection includes every candidate, including rejected records, with no 100-row cap. The normal DRF list remains paginated. The dashboard displays overall salary sum/minimum/maximum/average and per-role count/sum/minimum/maximum/average. Its minimum-applications filter generates SQL GROUP BY/HAVING; invalid filter values display form errors and use the default threshold of one.
